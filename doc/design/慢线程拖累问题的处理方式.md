## 慢线程拖累问题的处理方式

---

### aria2 的应对

aria2 有**三层防御**，但并非主动"抢活"：

| 机制 | 原理 | 源码位置 |
|------|------|----------|
| **超时踢出** | 连接长时间无数据 → 抛 `DlRetryEx` → 段归还调度器 | `AbstractCommand.cc:438` |
| **镜像自动切换** | 周期性比较各连接的 `avgDownloadSpeed`，发现更快镜像后取消当前慢连接、启用新连接 | `AbstractCommand.cc:222 findFasterRequest` |
| **段取消+重分配** | 慢连接被踢后，`cancelSegment` 记录已写位置，其他空闲连接可 `checkout` 该段继续 | `SegmentMan.cc:285` |

**不足**：aria2 的 HTTP 模式下，段一旦分配给某连接，只要它没超时/没出错，就**不会被主动抢走**。如果慢连接"还活着但很慢"，其他线程完成后只能空等。

---

### PCL2 的应对

PCL2 更主动一些：

| 机制 | 原理 |
|------|------|
| **速度过慢强制断开** | `DeltaTime > 5000ms && DeltaTime > RealDataCount` → 直接抛 `TimeoutException` 杀死线程 |
| **动态追加线程切最大碎片** | 全局速度低于下限时，找 `DownloadUndone` 最大的线程，从尾部 40% 处切一刀给新线程 |
| **源降级** | 慢源累计失败超限 → 标记 `IsFailed` → 后续不再分配 |

**不足**：PCL2 的"切最大碎片"只看**剩余量最大**，并不判断"谁最慢"。如果慢线程的剩余量不是最大的，就不会被切。而且它没有"快线程帮慢线程分担"的机制——快线程完成后就退出了。

---

### 我的设计：主动速度感知 + 工作窃取

两者都没有做到"**快线程主动帮慢线程分担**"。下面是完整方案：

```python
@dataclass
class Segment:
    start: int
    end: int
    written: int = 0
    owner_id: int = -1
    # 速度追踪
    bytes_history: deque = field(default_factory=lambda: deque(maxlen=10))
    
    @property
    def remaining(self): return self.end - (self.start + self.written)
    
    @property
    def speed(self):
        """最近 N 个采样周期的平均速度"""
        if len(self.bytes_history) < 2:
            return float('inf')  # 新段不判定为慢
        return sum(self.bytes_history) / len(self.bytes_history)


class WorkStealingScheduler:
    def __init__(self, total_size, num_workers, min_split=256*1024):
        self.segments: List[Segment] = [...]  # 初始预切
        self.min_split = min_split
        self.num_workers = num_workers
    
    # ─── 快线程完成后：不是退出，而是去帮最慢的段 ───
    def steal_or_checkout(self, worker_id) -> Optional[Segment]:
        # 1. 优先拿无主段（常规分配）
        for seg in self.segments:
            if seg.owner_id == -1 and seg.remaining > 0:
                seg.owner_id = worker_id
                return seg
        
        # 2. 无主段没了 → 找最慢的段，从尾部切一块给自己
        slowest = self._find_slowest_segment(exclude=worker_id)
        if slowest and slowest.remaining > self.min_split * 2:
            # 从尾部切出 40% 给当前快线程
            cut_point = slowest.end - int(slowest.remaining * 0.4)
            new_seg = Segment(start=cut_point, end=slowest.end, owner_id=worker_id)
            slowest.end = cut_point  # 缩小原段
            self.segments.append(new_seg)
            return new_seg
        
        return None  # 真的没活了
    
    def _find_slowest_segment(self, exclude) -> Optional[Segment]:
        candidates = [s for s in self.segments 
                      if s.owner_id != exclude 
                      and s.owner_id != -1
                      and s.remaining > self.min_split]
        if not candidates:
            return None
        return min(candidates, key=lambda s: s.speed)
```

**Worker 主循环**：

```python
async def worker(worker_id, url, path, scheduler, limiter):
    async with aiohttp.ClientSession() as session:
        while True:
            seg = scheduler.steal_or_checkout(worker_id)
            if seg is None:
                return  # 全部完成
            
            headers = {"Range": f"bytes={seg.start + seg.written}-{seg.end - 1}"}
            async with session.get(url, headers=headers) as resp:
                last_tick = time.monotonic()
                tick_bytes = 0
                
                async for chunk in resp.content.iter_chunked(64 * 1024):
                    if limiter:
                        await limiter.consume(len(chunk))
                    pwrite(path, chunk, seg.start + seg.written)
                    seg.written += len(chunk)
                    tick_bytes += len(chunk)
                    
                    # 每 500ms 记录一次速度采样
                    now = time.monotonic()
                    if now - last_tick >= 0.5:
                        seg.bytes_history.append(tick_bytes / (now - last_tick))
                        tick_bytes = 0
                        last_tick = now
            
            scheduler.complete(seg, worker_id)
```

### 核心设计要点

```
┌─────────────────────────────────────────────────┐
│           Work-Stealing Scheduler               │
├─────────────────────────────────────────────────┤
│                                                 │
│  快线程完成自己的段                              │
│       │                                         │
│       ▼                                         │
│  还有无主段？──Yes──→ 正常分配                   │
│       │                                         │
│      No                                         │
│       ▼                                         │
│  找速度最慢的段（speed 最低）                    │
│       │                                         │
│       ▼                                         │
│  剩余 > 2×min_split？──No──→ 退出（不切了）     │
│       │                                         │
│      Yes                                        │
│       ▼                                         │
│  从尾部切 40% 给快线程                           │
│  原慢线程继续拉前半部分（无感知）                │
│                                                 │
└─────────────────────────────────────────────────┘
```

| 设计点 | 说明 |
|--------|------|
| **速度采样** | 每 500ms 记录一次瞬时速度，滑动窗口取平均，避免抖动误判 |
| **切尾不切头** | 从慢段尾部切，慢线程正在写头部，互不冲突 |
| **无锁安全** | 切完后两段区间严格不重叠，pwrite 天然并发安全 |
| **慢线程无感知** | 慢线程的 `seg.end` 被缩小了，它写到新 end 就自然完成，不需要通知 |
| **最小碎片保护** | 剩余 < 2×min_split 时不再切，避免碎片化 |
| **多级策略** | 先拿无主段 → 再窃取最慢段 → 最后退出，优先级清晰 |

### 对比总结

| | aria2 | PCL2 | 本方案 |
|---|---|---|---|
| 慢线程检测 | 超时 + 镜像速度比较 | 5s 无数据判定 | **持续速度采样 + 滑动窗口** |
| 处理方式 | 踢掉重连/换镜像 | 杀线程 + 切最大碎片 | **快线程主动窃取最慢段尾部** |
| 快线程完成后 | 退出或拉下一无主段 | 退出 | **帮最慢的段分担** |
| 慢线程感知 | 被取消 | 被杀死 | **无感知，end 被缩小即可** |
| 适用场景 | 多镜像 | 多源 | **单源/多源均适用** |

这个"工作窃取"方案的核心优势：**快线程不空等，慢线程不被杀**，整体下载时间趋近于 `total_size / (N × avg_speed)` 的理论最优值。
